# SecureMailScope

**SecureMailScope** is a passive email network traffic analysis and forensic inspection platform. It reassembles TCP sessions from PCAP/PCAPNG network packet captures, inspects mail protocols (SMTP, IMAP, POP3), tracks STARTTLS handshake state transitions, parses TLS record layers and X.509 certificate chains, and evaluates security risk using a multi-layered, explainable forensic engine.

---

## 🏛 Architecture & Security Engines Separation

SecureMailScope enforces a strict architectural separation between deterministic forensic rules, unsupervised anomaly detection, and supervised cryptographic risk evaluation:

```
                               ┌────────────────────────┐
                               │       PCAP File        │
                               └───────────┬────────────┘
                                           │
                               ┌───────────▼────────────┐
                               │ TCP Session Reassembly │
                               └─────┬───────┬───────┬──┘
                                     │       │       │
                  ┌──────────────────┘       │       └──────────────────┐
                  │                          │                          │
           ┌──────▼─────────────────┐ ┌──────▼─────────────────┐ ┌──────▼─────────────────┐
           │  DETERMINISTIC RULES   │ │    ISOLATION FOREST    │ │  SUPERVISED ML MODEL    │
           │  (assessor.py & rules) │ │  (anomaly_detector.py) │ │ (crypto_risk_scorer.py) │
           │                        │ │                        │ │                         │
           │ • Explicit findings    │ │ • Unsupervised ML      │ │ • Whole-session ML      │
           │ • Expired certificate  │ │ • Flow metrics         │ │ • Complete feature vec  │
           │ • Broken cert chain    │ │ • Handshake timings    │ │ • Multi-class RF        │
           │ • Deprecated protocols │ │ • Baseline comparisons │ │ • Non-linear splits     │
           │ • Deductions & posture │ │ • Behavioral anomaly   │ │ • No rule penalty sums  │
           └───────────┬────────────┘ └──────┬─────────────────┘ └───────────┬─────────────┘
                       │                     │                               │
                       ▼                     ▼                               ▼
               Explicit Findings      Anomaly Flag & Score          AI Risk Classification
             (SEC-001, SEC-002...)    (Normal / Anomalous)         (LOW / MOD / HIGH / CRIT)
                                                                     + Probability-Weighted Score
                                                                     + Model Importances
```

### 1. Deterministic Security Rules Engine (`backend/app/assessment/`)
- Evaluates protocol, STARTTLS, TLS parameters, and X.509 certificate chains against established cryptographic RFCs and security standards.
- Emits explicit, explainable forensic findings (`SEC-001`, `SEC-002`, etc.) with granular severity (`CRITICAL`, `HIGH`, `MEDIUM`, `LOW`).
- Drives the transparent 0–100 Security Posture deduction score (`session["posture"]`).
- **Critical Rule**: Deterministic findings are strictly segregated from the AI model; findings and posture deductions are **never** added as manual penalty points to the AI score.

### 2. Behavioral Anomaly Detection (`backend/app/ml/anomaly_detector.py`)
- Employs an unsupervised **Isolation Forest** ensemble.
- Detects unusual, deviating email session behavior (e.g. packet timing anomalies, atypical payload byte ratios, flow duration deviations) relative to a learned baseline of normal mail communications.

### 3. AI Cryptographic Risk Scorer (`backend/app/ml/crypto_risk_scorer.py`)
- Evaluates the **overall cryptographic and security posture** of the complete observed email session using a supervised **Random Forest Classifier** (`CryptoRisk-RandomForestClassifier` v2.0.0).
- Takes the **complete session-level feature vector** simultaneously and predicts multi-class probabilities across `LOW`, `MODERATE`, `HIGH`, and `CRITICAL`.

> **Key Technical Principle:**
> *"SecureMailScope extracts session-level cryptographic and protocol features from passive PCAP analysis. These features are provided as a complete feature vector to the ML model. The model learns relationships between combinations of security characteristics and whole-session security labels. The final AI risk prediction is generated by the model rather than by summing manually assigned penalties for individual TLS/cipher features."*

## 🔬 How the AI Model Evaluates Risk

A cryptographic algorithm is **never judged in isolation**. Two sessions negotiating the exact same cipher suite (e.g., `TLS_AES_256_GCM_SHA384`) can possess entirely different security postures depending on the holistic session context:

| Context Attribute | Session A (Secure Posture) | Session B (Degraded Posture) |
| :--- | :--- | :--- |
| **Protocol & STARTTLS** | SMTP with completed `SECURE_TRANSITION` | SMTP with incomplete / stripped STARTTLS |
| **TLS Version** | Modern TLS 1.3 / 1.2 | TLS 1.2 |
| **Cipher Suite** | AES-256-GCM (AEAD) | AES-256-GCM (AEAD) |
| **Key Exchange** | Ephemeral ECDHE (PFS present) | Static RSA (No PFS) |
| **Leaf Certificate** | Valid, unexpired, trusted authority | Expired validity window |
| **Certificate Chain** | Complete, valid signatures, CA constraints ok | Invalid chain, unverified signatures |
| **Hostname Validation** | CN/SAN matches destination mail host | Hostname mismatch |
| **Application Payload** | Encrypted application data observed | Plaintext transmission / payload |
| **AI Risk Prediction** | **LOW Risk** (Score: ~95/100) | **HIGH / CRITICAL Risk** (Score: <40/100) |

The ML model learns non-linear decision splits across the combined feature vector rather than assigning isolated point values (e.g., no `+10 points for PFS`, `-20 points for expired cert`).

## 📊 Complete Session-Level Input Features

The ML model consumes 54 objective session observations extracted by `extract_session_features()`:

1. **Protocol Layer**: `protocol_is_smtp`, `protocol_is_imap`, `protocol_is_pop3`, `protocol_is_other`.
2. **STARTTLS State Machine**: `starttls_upgrade_supported`, `starttls_upgrade_requested`, `starttls_upgrade_accepted`, `starttls_transition_observed`, `starttls_is_incomplete`, `starttls_status_secure`, `starttls_status_direct_tls`, `starttls_status_none`.
3. **TLS Handshake & Version Indicators**: Categorical one-hot indicators (`tls_detected`, `tls_version_is_1_3`, `tls_version_is_1_2`, `tls_version_is_1_1`, `tls_version_is_1_0`, `tls_version_is_ssl3`, `tls_version_is_none`). No arbitrary linear version scores!
4. **Cipher Suite Attributes**: `cipher_is_aead`, `cipher_is_cbc`, `cipher_is_weak`, `cipher_is_modern`.
5. **Key Exchange & Forward Secrecy**: `kex_is_ecdhe`, `kex_is_dhe`, `kex_is_static_rsa`, `forward_secrecy_present`, `forward_secrecy_absent`.
6. **Data Transport**: `encrypted_application_data_observed`, `plaintext_payload_observed`.
7. **Leaf Certificate**: `certificate_present`, `certificate_is_valid`, `certificate_is_expired`, `days_until_expiry_norm`, `public_key_is_rsa`, `public_key_is_ec`, `public_key_is_substandard`, `signature_is_weak`, `certificate_is_self_signed`, `hostname_matches`, `hostname_mismatch`.
8. **Certificate Chain Validation**: `chain_observable`, `chain_complete`, `chain_status_valid`, `chain_status_invalid`, `chain_status_incomplete`, `certificate_count_norm`, `chain_signatures_verified`, `chain_ca_constraints_verified`, `chain_validity_periods_verified`, `chain_issuer_subject_linked`.
9. **Flow Metrics**: `packet_count_norm`, `duration_norm`, `client_bytes_ratio`.

*Note: Deterministic rule findings (`finding_count`, `posture_score`) are deliberately excluded from this vector to prevent circular dependencies.*

## ⚖️ Prediction Formulation & Presentation Calibration

1. **Multi-Class Prediction**:
   The `RandomForestClassifier` outputs multi-class probability distribution:
   $$\mathbf{P} = [P(\text{LOW}), P(\text{MODERATE}), P(\text{HIGH}), P(\text{CRITICAL})]$$
   The predicted classification label is $\text{argmax}(\mathbf{P})$.
2. **Confidence**:
   Confidence is the model's posterior probability for the predicted class: $P(\text{predicted\_label})$.
3. **Probability-Weighted Continuous AI Risk Score & Operational Risk Tier**:
   - **Continuous AI Risk Score (0–100)**: Evaluated directly from class-probability estimates over standard risk severity weights ($0.0, 33.0, 67.0, 100.0$):
     $$\text{Risk Score} = P(\text{LOW}) \times 0.0 + P(\text{MODERATE}) \times 33.0 + P(\text{HIGH}) \times 67.0 + P(\text{CRITICAL}) \times 100.0$$
   - **Operational Risk Tier**: Derived strictly from the continuous score using documented SOC score bands to guarantee tier/score consistency without contradiction:
     - `LOW`: $[0.0, 20.0]$ (Minimal risk / modern cryptography)
     - `MODERATE`: $[20.1, 50.0]$ (Limited configuration concern)
     - `HIGH`: $[50.1, 80.0]$ (Meaningful security weakness)
     - `CRITICAL`: $[80.1, 100.0]$ (Direct exposure / unencrypted / stripped STARTTLS)
   - **Model Predicted Class**: Preserves the Random Forest argmax probability ($\text{argmax}(\mathbf{P})$) for machine learning transparency.
   - It is clearly presented as an expected risk severity index mapped from class-probability estimates, not as a physical absolute constant or rule deduction sum.
4. **Session-Specific Risk Explanations (Perturbation-Based)**:
   Global feature importance describes the model overall. SecureMailScope's **Top Observed Risk Factors** are session-specific explanations derived from the current session feature vector and the model prediction.
   - For each active feature observed in the session, the engine performs a feature perturbation / neutralization ($X \to X_{\text{masked}}$) while holding all other session features unchanged.
   - It recalculates the predicted probability for the predicted risk class and computes the contribution:
     $$\Delta P = P_{\text{predicted\_class}}(X) - P_{\text{predicted\_class}}(X_{\text{masked}})$$
   - Only observed risk factors with a positive, material contribution ($\Delta P > 0$) are presented and ranked by their contribution.
   - **No normal/secure features as risks**: Evidence of security (e.g. `tls_version_is_1_3`, `encrypted_application_data_observed`, `certificate_is_valid`) is never presented in the risk factors list.
   - **Clean State for Secure Sessions**: Fully secure sessions with no contributing risk features cleanly display *"No significant risk factors observed"*.
   - **Zero Hardcoded Points**: Absolutely no manual penalties or bonuses (e.g. `-10 for weak cipher`, `+20 for valid cert`) are used; explanations derive dynamically from the trained model's decision function.

## ⚠️ Controlled Training Baseline & Limitations

> [!IMPORTANT]
> **Research & Demonstration Dataset Limitation**:
> The model is trained using controlled/synthetic labelled security-state data because a large labelled real-world enterprise email PCAP dataset is not currently available. It is intended for research, demonstration, and forensic prototyping and does not claim production-grade accuracy for unconstrained arbitrary network environments.

- **Archetypes Covered**: Pristine TLS 1.3/1.2 sessions, acceptable legacy configurations (CBC ciphers, non-PFS RSA key exchanges, incomplete chains), degraded/vulnerable configurations (expired certificates, invalid chain signatures, substandard keys, hostname mismatches), and critical failures (plaintext transmissions, stripped STARTTLS, NULL/export ciphers).
- **Extensibility**: The model learns boundaries based on these structured whole-session archetypes and is designed to be retrained on real-world labeled enterprise network captures as such data becomes available.

## 🎓 Mentor Explanation Summary

> *"In SecureMailScope, the cryptographic algorithm is not assigned an individual score. The system extracts the complete session security characteristics (protocol, STARTTLS transition, TLS record attributes, key exchange, certificate leaf validity, and chain verification status) and passes them together to the ML model. Deterministic rules are used only to identify explicit forensic findings and are not added as manual points to the AI score."*
